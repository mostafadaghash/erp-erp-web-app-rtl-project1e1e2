## Official contract

Architecture Baseline v1.7 and the Master Implementation Plan require Audit to capture, where applicable:

- Who
- What
- When
- Branch
- Entity / Document
- Reason
- Before
- After

Sensitive business actions must write their Audit record in the same successful transaction as the business action. The approved physical schema is `audit_logs(id, company_id, branch_id, user_id, action, entity_type, entity_id, reason, before_json, after_json, created_at)`.

## Implementation decisions

1. No migration `0023` and no new index. Phase 03 already owns the table, FKs, and the three frozen Audit indexes.
2. The service is append-only. It exposes record creation only and no UPDATE/DELETE path.
3. `created_at` is generated by PostgreSQL at execution time. Callers cannot backdate Audit chronology.
4. `branch_id`, `user_id`, `reason`, `before_json`, and `after_json` remain nullable exactly as defined by the approved schema; this supports system actions and actions where a field is not applicable.
5. Before/After snapshots must be JSON-compatible plain data. Unsupported/ambiguous runtime values are rejected before SQL instead of being silently lost or coerced.
6. The caller owns the transaction. Sensitive business effects and their Audit entry therefore commit or roll back together.
7. The service records facts supplied by the command layer; deciding which fields are required for a specific sensitive command remains that command's policy responsibility.
