## Official contract

Architecture Baseline v1.7 and the Master Implementation Plan require:

- `posting_batches` is the unified internal trace for one Business Posting and its Inventory/Financial/Customer/Supplier/Journal/Audit/Outbox effects;
- operation types are `POST / CORRECTION / REVERSAL / DELETE_REVERSAL`;
- `source_type + source_id` preserve source traceability;
- `reverses_posting_batch_id` is an optional self-reference used to link reversal/correction history to the original posting where applicable;
- `document_version` supports editing posted documents without rewriting historical ledgers;
- historical movements/ledger/journal effects are corrected by new reversal/correction postings, never by editing old history;
- `posted_at` is the real effect order and must be server-generated;
- critical posting and its effects commit together or roll back together.

## Implementation decisions

1. No migration `0023` and no new index; the Phase 03 physical schema and frozen Index Catalog already contain the required table, CHECK/FKs, and source trace index.
2. The service is insert-only. It does not expose UPDATE/DELETE APIs for historical posting batches.
3. `posted_at` is generated by PostgreSQL at execution time; callers cannot supply/backdate it.
4. `REVERSAL` and `DELETE_REVERSAL` require `reversesPostingBatchId`. `POST` cannot carry one. `CORRECTION` remains valid without one because the Baseline defines the self-reference as optional.
5. Whenever a reversal reference is supplied, the target batch is locked `FOR UPDATE` and must match the same `branch_id + source_type + source_id`; this prevents a reversal chain from silently crossing business sources.
6. The caller owns the transaction. Posting Batch creation and specialized posting effects therefore commit or roll back as one unit.
7. `documentVersion` is a positive integer at the service boundary; posted business documents start at version 1 and later edits advance it.
